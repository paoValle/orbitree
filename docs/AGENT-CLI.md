# The CLI, for the agent on the other side of the pipe

This is a contract, not documentation. Everything below is meant to be relied on: if a change
breaks one of these statements, the schema version changes and this file changes with it.

The design rule behind all of it: **an agent is a first-class user of this product.** It gets the
same operations as the app, machine-readable, with exit codes, and with the same safety rails the
GUI has — no more and no less.

## Running it

```bash
orbitree <command> [path] [options]      # a path inside the repository; "." by default
./bin/orbitree <command>                 # from a checkout, with no build step
```

## The envelope

With `--json`, stdout is **exactly one JSON object** and nothing else. Diagnostics, progress and
human prose go to stderr. So:

```jsonc
{
  "schemaVersion": 2,          // bumped when the shape of `data` changes
  "command": "status",         // the command that produced this
  "ok": true,
  "data": { /* command-specific */ }
}
```

and on failure, the same object with `ok: false` and **no `data`**:

```jsonc
{
  "schemaVersion": 2,
  "command": "status",
  "ok": false,
  "error": { "kind": "not-a-repository", "message": "…" }
}
```

`kind` is stable and closed; `message` is for a human and may change. Branch on `kind`, never on
the message text.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | unexpected failure |
| 2 | usage: an unknown command or option, or an argument git would read as a flag |
| 3 | `not-a-repository` |
| 4 | `git-failed`: `git` exited non-zero (see `stderr`, and the `doctor` command) |
| 5 | `confirmation-required`: a destructive operation without `--confirm` |

`error.kind` and the exit code agree: `kind` is the machine-readable form of the same fact.

## Discovery

```bash
orbitree schema                      # the envelope, the error kinds, the exit codes
orbitree schema --json               # (planned, P6) one JSON Schema per command
orbitree ops --json                  # every operation, its risk level and the argv it produces
orbitree doctor --json               # git version, platform, node, repository root
orbitree --help                      # generated by commander, always current
```

`orbitree ops --json` is the authoritative list of what `run` accepts. Its `risk` field is the
same value the executor uses to decide whether a confirmation is required. An operation that takes
paths takes them as `--arg` values: `--op discard --arg <path>` restores a tracked path, and
`--op clean --arg <path>` removes one git has never tracked — `restore` is a question about a
tracked path and does nothing to an untracked one. Without arguments `clean` takes every untracked
path in the repository. `--op discard-hunk --arg <path> --arg <hunk>` reverses one hunk of that
path's uncommitted diff: the patch is built from a read of the file inside the process that runs
git, so a caller names a hunk rather than supplying a patch. `--op branch-rename --arg <from> --arg
<to>` renames a branch without depending on which one is checked out, and `--op tag-delete --arg
<name>` removes a tag — which is `destructive`, because git has no safe form of it. The stash
operations take a selector: `--op stash-show --arg stash@{0}` reads its patch, `stash-apply` and
`stash-pop` put the work back, and `stash-drop` destroys the entry — the only one of the four that
is `destructive`. A commit takes a body as well as a summary: `--op commit --message <summary> --arg <body>`, and the
two reach git as two `-m`, so the blank line between them is git's rather than ours.

A conflicted path can also be written out whole — `--op resolve-file --arg <path> --arg <text>…` —
which is what an editor produces: the file replaced with text the caller decided on. The patch is
built inside the executor from a read of the file, so that text can only become the added lines of
that one file, and its reverse is `regenerate-conflict`. Neither writes the conflict away: the three
index stages survive until the path is added, so `git add` is still what resolves it.

Conflict resolution is per region: `--op resolve-conflict --arg <path> --arg <region> --arg
ours|theirs|both|custom` replaces one region of a conflicted file, where a region is counted from 0
in the file *as it is now* — resolving one renumbers the rest, so a caller re-reads before the next
call. The patch is built inside the executor from a read of the file, so `custom` text can only
become the added lines of that one region. It is `local`: the three index stages survive, and
`git checkout -m -- <path>` puts the conflict back.

`run` also answers with `reverse`: the command, its argv and its risk that put the repository back,
or `null` when there is nothing to undo with. Every reverse it names is an operation this product
has, so a caller can run it exactly the way it ran the operation. It is built from the `before` the caller supplies — the commit HEAD was on, the
branch that was checked out, and the sha of every branch and tag — because nothing in the repository
afterwards says where it was, and a reverse computed from a guess is worse than none. `null` means
one of three things: the operation destroyed work that was never committed, its reverse is a decision
rather than a command (a force push), or the state before was not sent.

The risk names below are what decide whether a confirmation is required:

```
read        nothing changes
local       changes this repository on this disk
remote      talks to another machine
destructive needs a confirmation token, or a --dry-run
```

## Reading a repository

```bash
orbitree status [path] --json
orbitree graph  [path] --json [--limit 200] [--all] [--rev <rev>] [--file <path>] [--hide <ref>]…
orbitree refs   [path] --json
orbitree worktrees [path] --json
orbitree remotes [path] --json
orbitree identity [path] --json
orbitree credential [path] --host <host> [--protocol https] --json
orbitree diff   [path] --json [--rev <rev>] [--cached | --unstaged] [--path <path>]
orbitree show   [path] --json [--rev <rev>]
orbitree blame  [path] --file <file> --json [--rev <rev>]
orbitree compare [path] --left <ref> --right <ref> --json [--limit 500]
```

`status` returns the working tree exactly as `readStatus()` does in the app: `head`
(`branch` / `detached` / `unborn`, with `ahead`/`behind` when tracking), `entries` (each with
`kind`, `index`, `worktree`, `path`, and the raw porcelain record it came from), the
unmodelled `headers`, and `pending` — the operation the repository stopped in the middle of,
one of `merge`, `cherry-pick`, `rebase`, or `null` when nothing is under way. `pending` comes from
three separate `git rev-parse -q --verify` reads (`MERGE_HEAD`, `CHERRY_PICK_HEAD`,
`REBASE_HEAD`), because a multi-argument `--verify` exits 1 on the first missing name and loses
the other two answers. An empty, unborn or detached repository is not an error: `head` says so,
and `orbitree graph` on an unborn one exits 4 because there is no history to read.

`graph` returns `commits`, `rows` (`hash`, `lane`, `through`, `incoming`, `outgoing`), `edges`
(`childRow`, `childLane`, `parentRow`, `parentLane`, `parentIndex`), `laneCount`, `total`,
`truncated`, `refs`, `rev` (the revision read, `HEAD` by default), `wip` and `stashes`.

`wip` is the working tree as the node above the first commit, with `on` (the commit HEAD sits on,
`null` when there is none), `staged`, `unstaged`, `conflicted`, `untracked` and `dirty`. It is not
a member of `rows` — the layout is a pure function of the DAG and the working tree is not a commit
— so `row 0` is still the newest commit.

`stashes` is the stash list, newest first, and is empty for a reading of one revision: a history
filtered to one branch is a picture of that branch. With `--all` every entry is named as a starting
point, because a stash older than `refs/stash` is reachable from nothing but that ref's reflog, and
`total` counts them for the same reason — `--all` here means the repository's whole picture. A row
whose commit is a stash carries its selector in `stash`, so a caller does not have to guess from a
subject that reads `On main: …`.

`hidden` is the list of names the picture is not drawing, and `graph --hide <ref>` (repeatable) is
how a caller asks for one: the commits left out are the ones only a hidden name can still reach, so
the layout is laid over what remains and no line goes down to nothing. It is a question about the
*picture* — nothing is written, and `total` still describes the history that was read. HEAD is always
among the visible names, because the commit somebody is standing on must not vanish from their own
picture.

`graph --file <path>` is the history of one file: only the commits git says touched that path, laid
out by the same function that lays out the whole repository, so `rows`, `edges` and `laneCount` mean
what they mean everywhere else. The simplification is git's — a merge whose result matches one side is
not a commit that changed the path — and `total` counts the same set, so `truncated` still compares the
window with the history it came from. A path nothing ever touched is an empty history rather than an
error. Note what the window does **not** have: its pane for this is reached from the working tree's
file list, so a file with nothing uncommitted has no row to click yet.

`total` is how many commits
the read history holds (`HEAD`, the revision named by `--rev`, or every ref with `--all`),
`truncated` is `commits.length < total`, and the human output's first line says
which it is: `14 commits · 1 lane`, or `2000 of 2053 commits · 2 lanes` when `--limit` cut the
history. Row `0` is the newest commit; the picture is complete without drawing anything.

`diff` answers one of three different questions, chosen by the flags, because a staged change
and an unstaged change are not the same comparison:

| invocation | the question | git argv |
|---|---|---|
| `diff` | the working tree against a revision | `git diff HEAD` |
| `diff --cached` | the index against a revision (`--rev`, `HEAD` by default) | `git diff --cached HEAD` |
| `diff --unstaged` | the working tree against the index | `git diff` |

`--cached` and `--unstaged` together is a usage error (exit 2): they are two questions, not a
filter and its inverse. Without either flag the behaviour is the working tree against `--rev`
(`HEAD` by default), unchanged from before those flags existed. In `--unstaged` mode `data.rev`
is `null`, because there is no revision on either side of that comparison.

Whatever the mode, `diff` returns `files`: each with `path` (unquoted, no
`a/`/`b/` prefix), `oldPath` when the file was renamed or copied, `status`, `binary`, and `hunks`.
An unmerged path is answered by git with a *combined* diff, which the patch parser refuses
outright; the app reads a conflicted file against `HEAD` instead, which is the plain two-tree
diff whose added lines are the conflict markers.
A hunk carries its `header`, `oldStart`, `newStart`, and `lines` (each a `kind` of `context`,
`add`, `del` or `note`) with `oldLines`/`newLines` recomputed from them. Every file and hunk
keeps `raw`, the exact text git printed, so nothing is lost. Without `--json`, the command
prints that raw patch, which is what a terminal wants.

`show` returns one commit as data: `commit` (the same fields `graph` gives, plus the message
`body`), `files` (the patch, exactly the shape `diff` returns), and `against` — `root`,
`parent` or `first-parent`, derived from how many parents the commit has rather than from the
caller's guess. A merge is shown as one diff against its **first parent**, never as an empty
patch and never as one diff per parent. Without `--json`, the command prints the metadata
(hash, author, date, subject, body) followed by the raw patch.

`blame` returns `lines`, one per line of the file: `line` (the number in the file as it is),
`originalLine` (the number in the commit that wrote it), `oid`, `summary`, `author`, `authorMail`,
`authorTime`, `content`, `boundary` (git reached the edge of the history it was asked about) and
`previous`. Without `--rev` the file is the one on disk, so a line that is not committed yet is
reported against the **all-zero** sha with git's own words, `Not Committed Yet`, as its author: a
caller that treats every `oid` as a commit to look up has a bug waiting for its first uncommitted
line. `--line-porcelain` is what the parser reads, which repeats the metadata per line so a truncated
read cannot shift the blame of the lines above it. Without `--json`, one line of output per line of the
file: the abbreviated commit, the date, the author and the text.

`compare` answers "what does each side have that the other does not", in both directions, from **one**
read of `git log --left-right --cherry-pick A...B`: `onlyLeft` and `onlyRight`, each a list of commits in
the shape `graph` uses, plus `records` — every commit git marked, with the `side` it was marked as. The
`--cherry-pick` part is why this is git's answer and not a set difference of two hash lists: a commit
whose patch is already on the other side is in neither list, so two branches that were rebased or
cherry-picked onto each other are reported as agreeing about the *work* rather than disagreeing about the
history. A limit is git's own `--max-count`, so a window that asks for one commit gets one and the lists
are what was read.

`credential` asks git's own helper whether a credential is stored for a host, and answers with
`{ available, username, hasPassword, entries, note }`. The **secret is never in the answer**, in
`--json` or in the text form: the product has no use for it, and a value that is never held cannot
leak. `entries` keeps the `key=value` lines git printed except that one, `note` is git's own words
when nothing is stored ("terminal prompts disabled", a locked keychain), and a missing credential is
an answer rather than an error. This is how a caller checks before pushing, and it is the reason the
product never writes a token anywhere of its own: the helper is the user's, and the token stays in it.

`remotes` returns `remotes`, one record per name — `name`, `fetchUrl`, `pushUrl` and the `raw`
lines git printed — because a remote is one thing with two URLs even though `git remote -v` prints
one line per URL. It is a read of the config and not of a machine: whether the other end answers is
`fetch`'s question, and this one never touches the network. Without `--json` it prints the name,
the fetch URL and, when it differs, the push URL.

`identity` returns the name, email and signing key commits would be made with, each as
`{ value, scope, origin }` — `scope` being `system`, `global`, `local`, `worktree` or `command`, and
`origin` the file git read it from. A part nobody set is `null` rather than an empty string, because
git refuses a commit without a name and that is worth knowing before trying. The resolution is git's
own: `git config` prints the records in the order it applies them, so the last occurrence of a key is
the one in force, and `records` keeps every `user.*` entry in that order so a key this version does
not name is still visible.

## Changing a repository

Every mutation goes through one command, and the operation name is the same string the app's
buttons use:

```bash
orbitree run [path] --op <op> [--arg <value>]… [--message <text>] [--dry-run] [--confirm <reason>] [--json]
```

```bash
# 1. Always look first. A dry run resolves the argv and runs nothing, so it needs no confirmation.
orbitree run . --op reset-hard --arg HEAD~1 --dry-run --json
# → {"data":{"op":"reset-hard","risk":"destructive","argv":["reset","--hard","HEAD~1"],"dryRun":true,…}}

# 2. Then decide. A reason is not a formality: it is recorded and shown to the user.
orbitree run . --op reset-hard --arg HEAD~1 --confirm "the last commit was the wrong file" --json
```

Rules an agent should assume:

- Without `--confirm`, a `destructive` operation exits 5 and changes nothing. There is no flag
  that turns the guard off.
- `--confirm` takes a **reason**, not a boolean. An empty reason is refused.
- `--dry-run` is always safe: no process is spawned, no lock is taken, nothing is written.
- Arguments that git would read as a flag are refused with exit 2 (`invalid-argument`) instead of
  being passed through. `--arg` values starting with `-` need `--arg=-like-this`.
- A failed `git` is a **value**, not an exception: exit 4, `stderr` populated, the repository in
  whatever state git left it. After a conflict, `status` reports `unmerged` entries — check them
  before assuming success.
- The `argv` in a result is the command as git was given it **with any credential masked**
  (`https://***@host/x.git`). Use `--dry-run` to see the same masked line before running; do not
  expect to read a password out of this output, and do not put one there.
- A failed remote command carries a `diagnosis` beside `stderr`: `{ failure, what, whatToDo }`, where
  `failure` is `ssh-key`, `host-key`, `token`, `offline`, `repository-not-found`, `diverged` or
  `refused-by-server`. It is `null` when the failure is not one of those — a missing revision, a
  conflict — and it never replaces `stderr`, so read both: the diagnosis says what to do, and git's
  words say what happened.

## What an agent should not do

- Do not run a `destructive` operation because a task description implies it. Show the argv
  (`--dry-run`), and let a human confirm the reason.
- Do not parse the human-readable output. It is for people and will change; use `--json`.
- Do not use the CLI to work around the invariants (a raw `git` in a shell is outside the
  product, and `--force-with-lease` is a decision, not a default).
- Do not assume `stderr` is empty on success: a fetch writes progress there. The same lines arrive
  as they happen and are also in the result, parsed, as `progress` — the last one, which is how far
  the command got: `{ phase, percent, detail, raw }`.

## Forge operations (P5) and agents (P6)

Planned, and the shape is already decided:

- `orbitree requests [path] --json` — open pull/merge requests, with the same schema for GitHub,
  GitLab and a self-hosted instance configured by API base URL.
- `orbitree checks [path] --json` — CI status per commit.
- `orbitree mcp` — an MCP server exposing every operation above, with the same schemas, plus
  read-only resources for the graph and the working tree.
- `orbitree watch [path] --json` — newline-delimited state changes, so waiting does not mean
  polling.

The rule those will follow is the one this file already states: anything the app can do is here,
with the same guards, and the schema version moves when the shape does.
