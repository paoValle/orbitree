# The CLI, for the agent on the other side of the pipe

This is a contract, not documentation. Everything below is meant to be relied on: if a change
breaks one of these statements, the schema version changes and this file changes with it.

The design rule behind all of it: **an agent is a first-class user of this product.** It gets the
same operations as the app, machine-readable, with exit codes, and with the same safety rails the
GUI has — no more and no less.

## Running it

```bash
orbitree <command> [path] [options]      # a path inside the repository; "." by default
./bin/orbitree <command>                 # from a checkout, with no build step
```

## The envelope

With `--json`, stdout is **exactly one JSON object** and nothing else. Diagnostics, progress and
human prose go to stderr. So:

```jsonc
{
  "schemaVersion": 2,          // bumped when the shape of `data` changes
  "command": "status",         // the command that produced this
  "ok": true,
  "data": { /* command-specific */ }
}
```

and on failure, the same object with `ok: false` and **no `data`**:

```jsonc
{
  "schemaVersion": 2,
  "command": "status",
  "ok": false,
  "error": { "kind": "not-a-repository", "message": "…" }
}
```

`kind` is stable and closed; `message` is for a human and may change. Branch on `kind`, never on
the message text.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | unexpected failure |
| 2 | usage: an unknown command or option, or an argument git would read as a flag |
| 3 | `not-a-repository` |
| 4 | `git-failed`: `git` exited non-zero (see `stderr`, and the `doctor` command) |
| 5 | `confirmation-required`: a destructive operation without `--confirm` |

`error.kind` and the exit code agree: `kind` is the machine-readable form of the same fact.

## Discovery

```bash
orbitree schema                      # the envelope, the error kinds, the exit codes
orbitree schema --json               # (planned, P6) one JSON Schema per command
orbitree ops --json                  # every operation, its risk level and the argv it produces
orbitree doctor --json               # git version, platform, node, repository root
orbitree --help                      # generated by commander, always current
```

`orbitree ops --json` is the authoritative list of what `run` accepts. Its `risk` field is the
same value the executor uses to decide whether a confirmation is required:

```
read        nothing changes
local       changes this repository on this disk
remote      talks to another machine
destructive needs a confirmation token, or a --dry-run
```

## Reading a repository

```bash
orbitree status [path] --json
orbitree graph  [path] --json [--limit 200] [--all] [--rev <rev>]
orbitree refs   [path] --json
orbitree diff   [path] --json [--rev <rev>] [--cached | --unstaged] [--path <path>]
orbitree show   [path] --json [--rev <rev>]
```

`status` returns the working tree exactly as `readStatus()` does in the app: `head`
(`branch` / `detached` / `unborn`, with `ahead`/`behind` when tracking), `entries` (each with
`kind`, `index`, `worktree`, `path`, and the raw porcelain record it came from), the
unmodelled `headers`, and `pending` — the operation the repository stopped in the middle of,
one of `merge`, `cherry-pick`, `rebase`, or `null` when nothing is under way. `pending` comes from
three separate `git rev-parse -q --verify` reads (`MERGE_HEAD`, `CHERRY_PICK_HEAD`,
`REBASE_HEAD`), because a multi-argument `--verify` exits 1 on the first missing name and loses
the other two answers. An empty, unborn or detached repository is not an error: `head` says so,
and `orbitree graph` on an unborn one exits 4 because there is no history to read.

`graph` returns `commits`, `rows` (`hash`, `lane`, `through`, `incoming`, `outgoing`), `edges`
(`childRow`, `childLane`, `parentRow`, `parentLane`, `parentIndex`), `laneCount`, `total`,
`truncated`, `refs`, `rev` (the revision read, `HEAD` by default), `wip` and `stashes`.

`wip` is the working tree as the node above the first commit, with `on` (the commit HEAD sits on,
`null` when there is none), `staged`, `unstaged`, `conflicted`, `untracked` and `dirty`. It is not
a member of `rows` — the layout is a pure function of the DAG and the working tree is not a commit
— so `row 0` is still the newest commit.

`stashes` is the stash list, newest first, and is empty for a reading of one revision: a history
filtered to one branch is a picture of that branch. With `--all` every entry is named as a starting
point, because a stash older than `refs/stash` is reachable from nothing but that ref's reflog, and
`total` counts them for the same reason — `--all` here means the repository's whole picture. A row
whose commit is a stash carries its selector in `stash`, so a caller does not have to guess from a
subject that reads `On main: …`.

`total` is how many commits
the read history holds (`HEAD`, the revision named by `--rev`, or every ref with `--all`),
`truncated` is `commits.length < total`, and the human output's first line says
which it is: `14 commits · 1 lane`, or `2000 of 2053 commits · 2 lanes` when `--limit` cut the
history. Row `0` is the newest commit; the picture is complete without drawing anything.

`diff` answers one of three different questions, chosen by the flags, because a staged change
and an unstaged change are not the same comparison:

| invocation | the question | git argv |
|---|---|---|
| `diff` | the working tree against a revision | `git diff HEAD` |
| `diff --cached` | the index against a revision (`--rev`, `HEAD` by default) | `git diff --cached HEAD` |
| `diff --unstaged` | the working tree against the index | `git diff` |

`--cached` and `--unstaged` together is a usage error (exit 2): they are two questions, not a
filter and its inverse. Without either flag the behaviour is the working tree against `--rev`
(`HEAD` by default), unchanged from before those flags existed. In `--unstaged` mode `data.rev`
is `null`, because there is no revision on either side of that comparison.

Whatever the mode, `diff` returns `files`: each with `path` (unquoted, no
`a/`/`b/` prefix), `oldPath` when the file was renamed or copied, `status`, `binary`, and `hunks`.
An unmerged path is answered by git with a *combined* diff, which the patch parser refuses
outright; the app reads a conflicted file against `HEAD` instead, which is the plain two-tree
diff whose added lines are the conflict markers.
A hunk carries its `header`, `oldStart`, `newStart`, and `lines` (each a `kind` of `context`,
`add`, `del` or `note`) with `oldLines`/`newLines` recomputed from them. Every file and hunk
keeps `raw`, the exact text git printed, so nothing is lost. Without `--json`, the command
prints that raw patch, which is what a terminal wants.

`show` returns one commit as data: `commit` (the same fields `graph` gives, plus the message
`body`), `files` (the patch, exactly the shape `diff` returns), and `against` — `root`,
`parent` or `first-parent`, derived from how many parents the commit has rather than from the
caller's guess. A merge is shown as one diff against its **first parent**, never as an empty
patch and never as one diff per parent. Without `--json`, the command prints the metadata
(hash, author, date, subject, body) followed by the raw patch.

## Changing a repository

Every mutation goes through one command, and the operation name is the same string the app's
buttons use:

```bash
orbitree run [path] --op <op> [--arg <value>]… [--message <text>] [--dry-run] [--confirm <reason>] [--json]
```

```bash
# 1. Always look first. A dry run resolves the argv and runs nothing, so it needs no confirmation.
orbitree run . --op reset-hard --arg HEAD~1 --dry-run --json
# → {"data":{"op":"reset-hard","risk":"destructive","argv":["reset","--hard","HEAD~1"],"dryRun":true,…}}

# 2. Then decide. A reason is not a formality: it is recorded and shown to the user.
orbitree run . --op reset-hard --arg HEAD~1 --confirm "the last commit was the wrong file" --json
```

Rules an agent should assume:

- Without `--confirm`, a `destructive` operation exits 5 and changes nothing. There is no flag
  that turns the guard off.
- `--confirm` takes a **reason**, not a boolean. An empty reason is refused.
- `--dry-run` is always safe: no process is spawned, no lock is taken, nothing is written.
- Arguments that git would read as a flag are refused with exit 2 (`invalid-argument`) instead of
  being passed through. `--arg` values starting with `-` need `--arg=-like-this`.
- A failed `git` is a **value**, not an exception: exit 4, `stderr` populated, the repository in
  whatever state git left it. After a conflict, `status` reports `unmerged` entries — check them
  before assuming success.

## What an agent should not do

- Do not run a `destructive` operation because a task description implies it. Show the argv
  (`--dry-run`), and let a human confirm the reason.
- Do not parse the human-readable output. It is for people and will change; use `--json`.
- Do not use the CLI to work around the invariants (a raw `git` in a shell is outside the
  product, and `--force-with-lease` is a decision, not a default).
- Do not assume `stderr` is empty on success: a fetch writes progress there.

## Forge operations (P5) and agents (P6)

Planned, and the shape is already decided:

- `orbitree requests [path] --json` — open pull/merge requests, with the same schema for GitHub,
  GitLab and a self-hosted instance configured by API base URL.
- `orbitree checks [path] --json` — CI status per commit.
- `orbitree mcp` — an MCP server exposing every operation above, with the same schemas, plus
  read-only resources for the graph and the working tree.
- `orbitree watch [path] --json` — newline-delimited state changes, so waiting does not mean
  polling.

The rule those will follow is the one this file already states: anything the app can do is here,
with the same guards, and the schema version moves when the shape does.
